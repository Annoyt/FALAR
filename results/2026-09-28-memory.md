# Память: что держит приложение, почему «падало втихую», что изменилось (28.09.2026)

Телефон: Redmi Note 10 Pro (Dimensity 1100, 7,5 ГБ ОЗУ, Android 13), с обычным набором приложений
владельца. Сборки 0.22.2 (до) и 0.22.3-разработка (после). Все цифры сняты на телефоне:
`dumpsys meminfo app.falar`, `ps -A -o RSS,NAME`, `/proc/meminfo`, `onTrimMemory` в `at.tsv`.

## Жалоба

«Запустил, закрыл — память не очищается; чистильщик выгружает около 4 ГБ, хотя в фоне ничего не
висело. После ~6000 знаков разговора, похоже, падает с нехваткой памяти, но втихую».

## Что нашлось

| Что | Замер |
|---|---|
| Процесс приложения после полной загрузки | 2,96 ГБ PSS, из них нативная куча 2,86 ГБ; Java-куча 72 МБ |
| llama-server (уточнитель) отдельным процессом | 1,27 ГБ RSS, после разборов до 1,42 ГБ |
| Вместе | около 4,2 ГБ — ровно то, что показывал чистильщик |
| Свободно на телефоне перед запуском | 277 МБ из 7,5 ГБ |
| Сигналы системы после загрузки уточнителя | уровни 10, 5 и **15 (критический)** через 5–35 с, каждый раз |
| Сигналы при холодном старте самого приложения | три критических за 30 с загрузки моделей, ещё без уточнителя |

1. **Память не отдавалась вовсе.** У движка не было освобождения моделей: ни распознавание, ни
   синтез, ни шесть сессий перевода не освобождались. Сервис жил после закрытия экрана
   (`START_STICKY`, нет `onTaskRemoved`), экран держал с ним связь, пока не уничтожен, а на
   Android 12+ «назад» экран не уничтожает, а сворачивает.
2. **«Тихое падение» — это система, убивающая процессы при критической нехватке памяти.** Java-куча
   72 МБ, до нехватки памяти в Java далеко; а 3,6 ГБ невытесняемой нативной памяти на телефоне с 8 ГБ
   загоняют систему в критическое состояние. Способ загрузки весов уточнителя этого не меняет:
   с `--load-mode none` пять критических сигналов за минуту, с `mmap` — семь.
3. **Переполнения окна уточнителя на репликах по 350 знаков не было** (11 реплик, 3688 знаков): фон
   ограничен восемью репликами. Но разбор был медленным — 25–42 с на реплику — и реплики приходили
   быстрее, чем разбирались: из 11 разобрано 5.
4. **Сервер держал четыре слота** (`n_slots = 4` в llama-server.log), а приложение шлёт по одному.

## Что изменилось и как проверено

| Проверка | Результат |
|---|---|
| Свернули «домой», микрофон выключен | через минуту «💤 останавливаюсь и отдаю память», процесс завершён, RSS 0 |
| «Назад» (на Android 13 — сворачивание) | так же, через минуту |
| Возвращение после завершения процесса | холодный старт, всё поднялось |
| Освобождение без завершения процесса | RSS 186 МБ + 543 МБ нативной кучи в сжатой подкачке — распределитель не возвращает освобождённое, поэтому процесс завершается |
| Уточнитель при запуске | не поднимается, приложение 2,4 ГБ, свободно 1682 МБ |
| Уточнитель перед разбором | проверка памяти: доступно 1866 МБ при пороге 216 → поднят за 6,6 с |
| Простой 45 с | выгружен сам, свободно снова 1986 МБ |
| Сервер | `n_slots = 1` |
| Токенизатор Hy-MT | 3,28 знака на токен по-португальски, 2,37 по-русски |
| Разбор с бюджетом фона (369 токенов запроса) | 10–20 с против 25–42 с без бюджета |

## Уточнитель во время живого разговора

В отдельном тестовом разговоре, 8 реплик, разбор каждые 3: проход разбора **ни разу не запустился**.
Системе было доступно 1164–1188 МБ при пороге 216, а подъём уточнителя разрешён при запасе от
1500 МБ сверху — все проходы отложены с видимой строкой в журнале. Порог не взят с потолка: при
подъёме с отображением файла доступная память падала на ~900 МБ (1866 → 966), и чтобы после
подъёма у системы оставалось хоть полгигабайта, нужно около 1,4–1,5 ГБ. Опустить порог до 900 МБ —
значит поднимать уточнитель у самого края: система в ответ убивает фоновые приложения, приходит
критический сигнал, и уточнитель выгружается посреди прохода. На этом телефоне ядро приложения и
уточнитель вместе во время разговора не помещаются; места прибавит только облегчение ядра.

## «Два перевода подряд» после правки — не эхо

Живым звуком эхо воспроизвести не удалось. Журнал владельца показал другое: после каждой правки
текста через 8–22 с шла строка «📖 выученное: перевод заменён (llm)». Правка ставила реплике новую
метку времени и стирала пометку «человек», уточнитель принимал её за свежую машинную и переводил
заново поверх исправления: «Posso oferecer uvas e maçãs» → «Posso sugerir uvas e maçãs»,
«Podemos fazer isso?» → «É assim que pode acontecer?». Правка текста теперь помечается как
человеческая, уточнитель такие реплики пропускает, облако их и так не трогало.

## Что осталось

- Приложение само по себе — 2,4 ГБ невытесняемой памяти, и его холодный старт тоже вызывает
  критические сигналы. Самый крупный кандидат на сокращение — перевод: декодер и декодер с кэшем
  грузятся отдельными сессиями с почти одинаковыми весами (по 220 МБ на направление). Объединённый
  декодер сэкономил бы около 440 МБ, но это другая выгрузка модели и новая проверка качества.
- На загрузке уточнителя система по-прежнему освобождает место, убивая чужие фоновые приложения.
  Сам Falar при этом больше не страдает.

## Из чего складываются 2,6 ГБ (замер по частям, холодный старт)

Резидентная память процесса до и после загрузки каждой части (`/proc/self/statm`, теперь пишется в
строках загрузки журнала), затем четыре перевода в отдельном тестовом разговоре. Два прогона.

| Часть | Файлы | Резидентно |
|---|---|---|
| Распознавание: parakeet, VAD, шумоподавитель | 640 МБ + мелочь | +785…791 МБ |
| **Перевод: шесть сессий OPUS-MT int8** | 2 × 584 МБ | **+1284…1324 МБ** |
| Озвучка: два голоса Piper | 2 × 63 МБ | +41…134 МБ |
| Процесс после четырёх переводов | | 2,63–2,66 ГБ RSS, PSS 2,55–2,58 ГБ |

Перевод — самая большая часть, и держит он примерно размер своих файлов. Настройки ONNX Runtime
этого не меняют:

| Способ загрузки перевода | Резидентно | Перевод длинной фразы |
|---|---|---|
| как всегда | +1284…1324 МБ | 0,47–0,72 с |
| без упаковки весов (`session.disable_prepacking`) | +1331…1386 МБ | 0,97–1,45 с — вдвое медленнее |
| без арены и шаблонов памяти | +1387 МБ | 0,57–0,74 с |

Значит, лишних копий внутри сессии нет, а лишнее — сами файлы: `decoder_model.onnx` и
`decoder_with_past_model.onnx` несут одни и те же веса декодера (≈216 МБ на направление) и грузятся
двумя сессиями. Объединённый декодер (одна сессия с веткой «с кэшем / без») должен снять около 430 МБ
— это следующий шаг, для него нужны новые файлы моделей.
