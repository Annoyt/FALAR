# OPUS-MT tc-big int8 ONNX — замер НА ТЕЛЕФОНЕ, 2026-09-10

Первое измерение MT на реальном ARM. Устройство — по-прежнему **не целевое**: Redmi Note 10 Pro,
Dimensity 1100 (4×A78 @2.6 + 4×A55), **без i8mm**, LPDDR4X, Android 13. См. оговорки в
`2026-09-10-dimensity1100-llamacpp.md`. На POCO X7 Pro (A725, i8mm, LPDDR5X) ожидать ×2–2.5 быстрее.

## Как запущено (без NDK, без Termux, без APK)

1. `optimum-cli export onnx --task text2text-generation-with-past` → три графа:
   `encoder_model`, `decoder_model` (первый шаг, отдаёт KV энкодера и декодера),
   `decoder_with_past_model` (шаги с кэшем). optimum-onnx откатил transformers на 4.57.6.
2. `onnxruntime.quantization.quantize_dynamic(weight_type=QInt8)`:
   encoder 140 МБ + decoder 228 + decoder_with_past 216 = **584 МБ на направление**
   (fp32 было 2.3 ГБ). Таблица эмбеддингов 61345×1024 продублирована в обоих декодерах —
   в приложении её можно вынести в общий инициализатор и сэкономить ~60 МБ int8.
3. Рантайм: официальный `onnxruntime-android` 1.29.0 AAR с Maven Central —
   `libonnxruntime.so` (32 МБ) + `libonnxruntime4j_jni.so` + `classes.jar` (Java API).
4. Драйвер: 106 строк Java (`OrtBench.java`) — жадный декод с KV-кэшем. Собран `javac --release 11`
   + D8 из `tools/r8.jar`, запущен **через `app_process`** из `/data/local/tmp`
   (`CLASSPATH=bench.dex LD_LIBRARY_PATH=/data/local/tmp/ort taskset f0 app_process …`),
   свойство `onnxruntime.native.path` указывает на каталог с .so. ORT сообщил провайдеры
   `[CPU, NNAPI, XNNPACK, WEBGPU]`; использован CPU, 4 потока, пин на большие ядра.
5. Токенизация — на ПК (`MarianTokenizer`, с `>>rus<<` и `</s>`), телефон получает id.
   Разбиение на предложения — то же, что в `mt_bench.py`.

## Корректность: телефон = ПК

| направление | chrF телефон | chrF ПК (тот же int8, жадный) | chrF CT2 beam-4 | id совпали с ПК |
|---|---|---|---|---|
| pt→ru | **65.61** | 65.26 | 67.26 | 39 / 40 |
| ru→pt | **62.92** | 62.92 | 65.25 | 40 / 40 |

Единственное расхождение — одна фраза, где NEON- и AVX2-ядра дали разный argmax при близких
логитах. Разница с beam-4 (~2 chrF) — цена жадного поиска; beam на телефоне пока не реализован.

## Задержка на Dimensity 1100 (4 потока, большие ядра, устройство холодное)

| | pt→ru | ru→pt |
|---|---|---|
| p50 на фразу | **0.21 с** | **0.17 с** |
| p95 | 0.36 с | 0.26 с |
| энкодер (медиана) | 27 мс | 25 мс |
| первый шаг декодера | 40 мс | 33 мс |
| **каждый следующий токен** | **15.5 мс** | **15.2 мс** |
| токенов на фразу (среднее) | 8.5 | 7.3 |
| загрузка трёх графов | 2.6 с | 2.4 с |

Для сравнения на том же телефоне: 1B-LLM Q4_0 — 2.5 с на фразу, 4B — 7.1 с. То есть
**Marian int8 через ORT в ~12 раз быстрее 1B-LLM и в ~35 раз быстрее 4B** при лучшем качестве,
чем NLLB. Строка «MT 250–400 мс» из бюджета `PLAN.md` §3 — **подтверждена с запасом** даже
на нецелевом чипе; на X7 Pro ожидать ~0.1 с.

Троттлинг здесь не измерялся (прогон 40 фраз длится ~9 с). По llama-замеру на этом же чипе
compute-bound часть теряет до −72% под длительной нагрузкой — для MT это энкодер и первый шаг,
т.е. худший случай ~0.4–0.5 с на фразу.

## Что это значит для архитектуры

- **MT перестал быть узким местом.** 0.2 с из бюджета 1.4–2.8 с; главное теперь — ASR (§1).
- **ONNX Runtime — проверенный рантайм для OPUS-MT на Android**, а раз sherpa-onnx тоже сидит на ORT,
  весь стек (VAD + ASR + MT + TTS) живёт в одной библиотеке.
- Память: 584 МБ на направление на диске; резидентно ~0.6 ГБ на оба с расшаренными эмбеддингами.
- Открытые задачи: beam-4 на телефоне (+2 chrF, ×~2 по времени декода), выделение общей таблицы
  эмбеддингов, замер на X7 Pro.
