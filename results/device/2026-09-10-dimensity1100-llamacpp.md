# Замер на реальном ARM: llama.cpp, Dimensity 1100

Дата: 2026-09-10. Первые измерения проекта на настоящем железе — до этого всё
в `REPORT.md` снималось на эмуляции `poco-cpu` (потоки ПК), а `PLAN.md` §3 был экстраполяцией.

## Устройство — ВНИМАНИЕ, НЕ ЦЕЛЕВОЕ

| | подключённое | цель |
|---|---|---|
| Модель | Redmi Note 10 Pro (M2104K10AC) | POCO X7 Pro |
| SoC | Dimensity 1100 (MT6891) | Dimensity 8400 Ultra |
| Ядра | 4×A78 @2.6 + 4×A55 @2.0 | 1×A725 @3.25 + 3×@3.0 + 4×@2.1 |
| ISA | Armv8.2, `asimddp`, **без i8mm** | Armv9.2, **i8mm обязателен** |
| RAM | 8 ГБ, LPDDR4X | 8/12 ГБ, LPDDR5X-8533 |
| Android | 13 (SDK 33) | 15/16 |

Все числа ниже — **нижняя граница** для X7 Pro. Разрыв ожидается 2–2.5× по совокупности
IPC, частот, i8mm и пропускной способности памяти (генерация токенов упирается в память).

## Метод

Официальная сборка `llama-b10883-bin-android-arm64` из релизов ggml-org, распакована
в `/data/local/tmp/lb`, запуск напрямую через `adb shell` с `LD_LIBRARY_PATH=.`.
**Termux и NDK не нужны** — `/data/local/tmp` исполняемый.

Сборка содержит рантайм-диспетч по ревизии ARM. Загрузился
`libggml-cpu-android_armv8.2_2.so` — подтверждает отсутствие i8mm. На X7 Pro
загрузился бы `libggml-cpu-android_armv9.2_2.so`.

## Результат: Gemma 3 4B Q4_K_M (модель «режима качества» из REPORT.md)

`taskset f0` (только большие ядра), `-t 4`, `-r 2`:

| тест | t/s |
|---|---|
| pp20 | 23.74 ± 0.59 |
| pp512 | 22.30 ± 0.67 |
| tg30 | **4.81 ± 0.01** |
| tg128 | 4.06 ± 0.85 |

**Перевод одной фразы (20 вх / 30 вых токенов) = 0.84 + 6.24 = ≈ 7.1 с.**

В `REPORT.md` для этой же модели указано 1.7 с — это была цифра с ПК. На реальном ARM
она в 4 раза хуже, и это ещё без ASR и TTS.

Экстраполяция на X7 Pro (×2–2.5): tg ≈ 9–12 t/s, pp ≈ 40–50 t/s → **≈ 3.3–3.8 с только
на MT**. Это совпадает с оценкой `PLAN.md` §3 (4B: 40–65 pp / 9–15 tg, «NOT VIABLE»)
и подтверждает её: 4B не годится для живого перевода ни на одном из двух устройств.

## Результат: потоки

| потоки | tg30, t/s |
|---|---|
| 4 (большие) | 4.96 |
| 8 (все) | **3.27** |

**8 потоков хуже 4 на 34%.** Подтверждает `PLAN.md` §5: гонять на все ядра нельзя,
малые A55 становятся бутылочным горлышком в memory-bound генерации. На X7 Pro
кластер тоже асимметричный (4×2.1 ГГц), так что правило переносится.

## Выводы для проекта

1. **Режим «качество» на 4B в REPORT.md нежизнеспособен.** Нужен либо 1–1.8B, либо
   отказ от LLM в пользу encoder-decoder (Marian из `PLAN.md` §1 — один прогон энкодера
   плюс короткий beam-декод, а не авторегрессия по 30 токенов).
2. **Пинить ровно на большие ядра.** `-t 4` + `taskset f0`, не `-t 8`.
3. Официальные Android-бинарники llama.cpp снимают необходимость в Termux — любой
   дальнейший замер делается одной командой `adb shell`.

## Результат: Q4_0 против Q4_K_M (утверждение PLAN.md §1)

Одна и та же модель, одно устройство: Q4_K_M реквантизован в Q4_0 прямо на телефоне
через `llama-quantize --allow-requantize` (2368 МиБ -> 2248 МиБ). Качество при
реквантизации падает, но для замера пропускной способности важен только тип квантования.

| | Q4_0 | Q4_K_M | отношение |
|---|---|---|---|
| pp512, холодное устройство | 30.60 ± 2.22 | 20.42 ± 1.19 | **1.50x** |
| pp512, прогретое устройство | 8.51 ± 1.38 | 5.15 ± 1.51 | **1.65x** |
| tg30, чистый прогон r=4 | 3.35 ± 0.92 | 3.61 ± 0.70 | **неразличимо** |

**Вывод: Q4_0 быстрее только на префилле (в 1.5-1.65 раза, воспроизводимо на двух
температурных режимах). На генерации разницы нет — доверительные интервалы перекрываются.**

Первый шумный прогон показал у Q4_0 вдвое худшую генерацию (2.21 против 4.50); чистый
повтор с 4 повторами это не подтвердил. Разброс +-27% — считать тот результат артефактом.

Почему это важно для проекта: перевод фразы — это ~20 входных токенов и ~30 выходных,
то есть нагрузка **доминируется генерацией**, где выигрыша нет. Экономия на префилле
(0.60 с против 1.11 с на холодном устройстве) не окупает ничего заметного.

### KleidiAI в официальной сборке НЕТ

`strings` по `libggml-cpu-android_armv8.2_2.so` и `...armv9.2_2.so`: 0 упоминаний kleidi,
но ~910 символов aarch64-репакинга. То есть официальные бинарники ggml-org используют
собственный ARM-путь llama.cpp, а не KleidiAI. Замер выше относится к нему.

Утверждение §1 плана («у KleidiAI ядра только под Q4_0/Q8_0, поэтому шипить Q4_0»)
этим тестом **не проверено** — оно про KleidiAI, которого в сборке нет. Проверена более
общая формулировка «Q4_0 быстрее на ARM», и она подтвердилась только для префилла.

## Результат: троттлинг поддлительной нагрузкой

После ~40 минут непрерывных бенчмарков, те же команды на том же устройстве:

| тест | холодное | прогретое | падение |
|---|---|---|---|
| pp512 (Q4_0) | 30.60 | 8.51 | **-72%** |
| pp512 (Q4_K_M) | 20.42 | 5.15 | **-75%** |
| tg30 (Q4_K_M) | 4.96 | 3.61 | **-27%** |

**Префилл троттлит примерно в 2.5 раза сильнее генерации.** Физически логично: троттлинг
режет частоты, что бьёт по compute-bound работе (префилл), тогда как генерация упирается
в память и от частот зависит слабее.

`PLAN.md` §1 предсказывал «25-40% потери в установившемся режиме» — для генерации это
верно (-27%), для префилла это **сильная недооценка** (-72%). Для приложения, которое
работает в кармане часами, планировать надо по прогретым числам, а не по холодным.

## Результат: 1B против 4B — размерный класс решает

`unsloth/gemma-3-1b-it-Q4_0.gguf` (722 МБ, размер совпал с HF побайтно), холодное устройство,
`taskset f0`, `-t 4`, `-r 3`:

| тест | 1B Q4_0 | 4B Q4_K_M | выигрыш |
|---|---|---|---|
| pp20 | 78.96 ± 30.47 | 23.74 ± 0.59 | 3.3x |
| pp512 | 103.12 ± 4.19 | 22.30 ± 0.67 | 4.6x |
| tg30 | **13.24 ± 5.81** | 4.81 ± 0.01 | **2.8x** |
| tg128 | 12.27 ± 6.40 | 4.06 ± 0.85 | 3.0x |

**Перевод фразы (20 вх / 30 вых):**

| | холодное | прогретое (по измеренным коэффициентам -72% pp / -27% tg) |
|---|---|---|
| 1B Q4_0 | 0.25 + 2.27 = **2.5 с** | 0.9 + 3.1 = **4.0 с** |
| 4B Q4_K_M | 0.84 + 6.24 = **7.1 с** | 3.0 + 8.5 = **11.5 с** |

Экстраполяция на X7 Pro (x2-2.5): 1B даёт **~1.2 с холодным и ~2 с прогретым** только на MT.
Это уже вписывается в бюджет §3, тогда как 4B не вписывается ни при каких условиях.

Разброс на 1B большой (tg30 +-5.81, pp20 +-30.47) — устройство успевало прогреваться между
повторами. Порядок величины надёжен, точные числа нет.

**Вывод: 4B из REPORT.md заменить на 1-2B.** И даже так LLM проигрывает encoder-decoder
из §1: Marian делает один прогон энкодера плюс короткий beam-декод вместо авторегрессии
по 30 токенам, то есть у него нет главной статьи расходов, которая тут и меряется.

## Не измерено


- **Q4_0 с i8mm.** Измерено без i8mm. На X7 Pro (armv9.2) загрузится другой вариант
  бэкенда, и соотношение может отличаться — особенно на префилле, где i8mm даёт больше всего.
- **whisper.cpp** — Android-бинарников в релизах нет (только `ubuntu-arm64` под glibc,
  на bionic не запустится). Нужен NDK или Termux.
- **CTranslate2 / Marian** — Android-сборки не существует (OpenNMT/CTranslate2 issue #1683).
  Основной кандидат MT из §1 на устройстве напрямую померить нельзя, только через ONNX Runtime.
