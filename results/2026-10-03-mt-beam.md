# Перебор вариантов при переводе (луч): замер на ПК «как одно ядро» (03.10.2026)

Владелец, 03.10: «надо попробовать ещё раз замер по качеству по новым тестам сделать сначала на компьютере,
а потом выдавать уже какие-то предложения; все тесты сначала валидируются на компе с ограничением на одно
ядро … нужно эмулировать для проверок данные условия на ПК».

Сейчас приложение переводит жадно: на каждом шаге берёт один самый вероятный кусок слова и не
возвращается. Луч держит несколько лучших черновиков и в конце выбирает лучший целиком. Прежний замер
(02.10, [mt-metrics](2026-10-02-mt-metrics.md)) мерил луч в CTranslate2, а не в коде приложения, и без
времени.

## Что сделано

`Engine.beamKv` — перебор в коде приложения, за флагом `Engine.mtBeam` (по умолчанию 1 — нынешний жадный
путь, приложение не меняется). Отбор — как у CTranslate2 с patience 1 и HF с early_stopping: на шаге
2·ширина лучших продолжений по сумме логвероятностей, конец фразы среди первых «ширина» — готовый
вариант, готовых «ширина» — стоп, выбор — по средней логвероятности на кусок (норма длины 1,0).

**Находка до замера: пакет черновиков меняет вероятности.** Модели перевода сжаты в int8 с
динамическим квантованием активаций, и масштаб квантования один на весь вход. Если черновики идут через
декодер одним пакетом, вероятности каждого зависят от соседей по пакету: логиты строки сдвигаются до
0,4–0,5 (опыт: одна и та же строка в пакете с разными соседями). Поэтому два способа:

- **пакетом** — один вызов декодера на шаг для всех черновиков: дёшево, но вероятности с шумом;
- **по одному** (`Engine.mtBeamSeq`) — каждый черновик своим вызовом: вероятности ровно как у жадного
  пути, но вызовов в «ширина» раз больше.

CTranslate2 (прежний замер) квантует активации по строкам, поэтому у него этого шума нет.

**Сверка** (`bench/quality/BeamCheck.java`, 80 + 80 фраз набора Tatoeba):

| | pt → ru | ru → pt |
|---|---|---|
| ширина 1 = жадный путь, оба способа | 81 из 81 предложения | 83 из 83 |
| по одному: оценка луча = пересчёту выбранного варианта по одному куску | 81 из 81, разница ≤ 5·10⁻¹⁵ | 83 из 83, ≤ 7·10⁻¹⁵ |
| пакетом: то же | 0–2 из 81, разница до 0,22 | 2–4 из 83, до 0,21 |
| ширина 4, по одному: выбранный вариант не хуже жадного по оценке модели | 80 из 81 | 83 из 83 |
| ширина 4, пакетом: то же | 48 из 81 | 51 из 83 |

Перестановка прошлого декодера у способов общая, и по одному она сходится до последнего знака — код
верен; расхождение пакета — шум квантования, а не ошибка перестановки.

## Как мерится

- **Качество** — тот же код приложения на столе (`bench/quality/MtRun.java`, ONNX Runtime 1.29.0, модели
  телефона), наборы Tatoeba 1000 / 927 пар и прежние 40 + 40 «ситуаций»; chrF, chrF++, COMET, парный
  бутстрэп против жадного (`tools/mt_metrics.py --compare`).
- **Одно ядро.** Процесс привязан к одному ядру (`taskset -c N`), у ONNX Runtime один поток
  (`-Dfalar.threads=1`, на телефоне сейчас 4), сборщик мусора однопоточный. Время на фразу — без первых
  20 фраз (разогрев). Решающее время — отдельный прогон, где варианты идут по очереди на каждой фразе
  (нагрузка ПК от других задач делится поровну).
- ПК — i5-11400H (6 ядер, AVX-512 VNNI). Ядро ПК быстрее ядра телефона, поэтому переносится отношение
  «луч / жадный», а не миллисекунды; на телефоне — отдельный замер.

## Критерии (записаны до замера)

1. **Лучше по качеству:** на наборе Tatoeba разница COMET с жадным — 95 % интервал целиком выше нуля в
   pt → ru, а в ru → pt интервал не целиком ниже нуля (не хуже). chrF — для справки.
2. **Терпимо по времени:** среднее время на фразу на одном ядре — не больше 1,9 жадного. Откуда 1,9: на
   телефоне жадный перевод — 210 мс в среднем (PLAN §3), бюджет этапа — 400 мс; 400 / 210 ≈ 1,9, если
   отношение перенесётся на телефон (проверить там).
3. Из прошедших 1 и 2 предлагается самая узкая ширина с лучшим COMET — и только для замера на телефоне.
   Не прошёл никто — предложений «включить» нет.
4. Прогоны детерминированы: 60 случайных фраз каждого варианта, переведённые заново, должны совпасть
   (ПК с андервольтом: ошибки под нагрузкой бывают тихими).

### Ускорение отбора (владелец: «сначала 1, потом 2»)

Отбор и перестановка перенесены в два крошечных ONNX-графа (`BeamOps`, 454 и 1344 байта; собирает и
сверяет с numpy `tools/mt_beam_ops.py`): **select** — log-softmax строки и K лучших кусков по логитам
(LogSoftmax + TopK + GatherElements, `<pad>` запрещён через ScatterElements), **gather** — строки прошлого
декодера под новых родителей и K/V кодировщика на пакет (Gather по оси 0). ONNX Runtime считает их
векторно, а Java получает только 2·ширина кусков на черновик. Модели перевода не меняются.

- Переводы — те же: ширины 2 и 4 на всех 1040 + 967 фразах совпали с прежними прогонами, значит, таблица
  качества выше остаётся в силе. Сверка: ширина 1 = жадный путь (164 из 164 предложений); по одному
  оценка луча = пересчёту до 6·10⁻⁴ (логвероятности теперь float из графа, раньше — double).
- Отбор: 28,2 → **6,6 мс** на фразу, перестановка: 5,5 → **2,0 мс**.

| время вперемешку, одно ядро, 240 фраз (`results/mt_beam_time2_*.json`) | pt → ru: среднее | p95 | к жадному | ru → pt: среднее | p95 | к жадному |
|---|---|---|---|---|---|---|
| жадный | 132 мс | 219 мс | 1 | 130 мс | 245 мс | 1 |
| ширина 2, пакетом | 135 | 229 | 1,03 | 134 | 261 | 1,03 |

Ширина 4 теперь добавляет к фразе около 18 мс на одном ядре ПК (было около 45): примерно 10 мс — сам
декодер на пакет из четырёх, 6,6 — отбор, 2 — перестановка.

Проходит одна ширина 4 пакетом — значит, по критерию 3 она кандидат **для замера на телефоне**, а не для
выпуска. Прибавка честная, но небольшая: COMET +0,002–0,004. Меняется перевод у 27–30 % фраз, заметно
(COMET больше чем на ±0,03) — у 10–15 %, и среди них лучших больше, чем худших, но не намного: pt → ru —
54 заметно лучше и 43 заметно хуже из 269 изменившихся, ru → pt — 86 и 56 из 280.

## Ограничения

- Tatoeba — короткие учебные фразы без ошибок распознавания; на живой речи прибавка может быть другой, а
  40 «ситуаций» её не различают.
- Ядро ПК (i5-11400H, AVX-512 VNNI) не равно ядру телефона, и на телефоне перевод идёт в 4 потока;
  переносится отношение, а не миллисекунды — и то лишь как ожидание до замера на телефоне.
- Пока шли прогоны, ПК был занят и другими задачами (нагрузка 2,5–3,8); замер вперемешку делит её между
  вариантами поровну, отдельные прогоны качества — нет, поэтому время в них не решающее.

## Как повторить

```bash
# сверка: ширина 1 = жадный, по одному оценка = пересчёту
java -cp … dev.agenttranslator.BeamCheck models pt2ru data/mt_test/tatoeba.json 80 1 2 4
# качество на одном ядре
taskset -c 2 java -XX:+UseSerialGC -Dfalar.threads=1 -Dfalar.beam=4 -cp … dev.agenttranslator.MtRun \
  models pt2ru out.json data/mt_test/tatoeba.json=tatoeba data/test_set.json=situations
.venv-comet/bin/python tools/mt_metrics.py --threads 4 out.json
.venv-comet/bin/python tools/mt_metrics.py --compare bench/quality/baseline/mt_pt2ru.json out.json   # A — жадный
# время вперемешку
taskset -c 4 java -XX:+UseSerialGC -Dfalar.threads=1 -cp … dev.agenttranslator.TimeRun \
  models pt2ru time.json 1,2,4,2s,4s 200 data/mt_test/tatoeba.json=tatoeba data/test_set.json=situations
```

Классы — как в `bench/quality/gate.sh` (javac Engine.java, sherpa-java-api, MtRun/BeamCheck/TimeRun; ONNX
Runtime 1.29.0 с Maven Central).
